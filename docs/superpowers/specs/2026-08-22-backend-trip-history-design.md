# GreenerCart Backend Trip History Design

**Date:** 2026-08-22

**Status:** Approved for implementation planning

**Scope:** SQLite trip persistence, REST endpoints, live-mode frontend repository, and one-time browser-history migration

## 1. Goal

Replace browser-only trip history with a backend-backed implementation in live API mode while preserving the frontend's existing `TripRepository` contract and approved save behavior. Receipt results save automatically after calculation. Manual results save only after the user selects **Save to history**. Mock mode remains self-contained through `localStorage`.

The implementation will reuse the useful SQLite foundation from `origin/History-implementation`, but its calculation-coupled save behavior and history response contract will be replaced rather than merged unchanged.

## 2. Product Decisions

- Live mode uses SQLite-backed history through an HTTP repository.
- Mock mode continues to use the current `LocalStorageTripRepository`.
- Receipt and manual calculation endpoints calculate only; they do not persist history.
- The frontend remains responsible for deciding when a calculated result is saved.
- Existing browser trips migrate automatically when live history is first used.
- Migration preserves each trip's original `savedAt` value.
- SQLite assigns new canonical IDs to migrated trips.
- Migration is idempotent and safe to retry.
- Local records are removed only after the complete migration succeeds.
- There is no account or multi-user history isolation in this scope.

## 3. Shared Domain Contract

The REST API represents the same normalized domain model used by the frontend:

```ts
type TripSource = "receipt" | "manual";

interface SavedTripItem {
  id: string;
  name: string;
  co2eKg: number;
}

interface NewTrip {
  source: TripSource;
  totalCo2eKg: number;
  items: SavedTripItem[];
}

interface SavedTrip extends NewTrip {
  id: string;
  savedAt: string;
}
```

The HTTP JSON contract uses these camel-case field names directly. IDs are opaque strings even if SQLite uses integer row IDs internally. Canonical backend IDs use a backend-owned representation distinct from the UUIDs generated by the current browser repository, so a canonical reference cannot collide with a migrated local reference. `savedAt` is an ISO 8601 UTC timestamp.

Regular saves accept `NewTrip`; persistence assigns and returns the canonical ID and timestamp. Migration is the only path allowed to supply an existing timestamp.

## 4. REST API

### `GET /api/trips`

Returns a JSON array of complete `SavedTrip` objects, newest first. This endpoint returns all trips for the current single-user hackathon store. The frontend derives its six-upload Progress view from the returned collection.

### `GET /api/trips/{id}`

Treats the path value as a durable trip reference. It first resolves a canonical backend ID and then the unique browser import key. This keeps `/history/{localStorageId}` routes and bookmarks working after migration. The response is always the canonical backend `SavedTrip`, even when lookup used a legacy import key. An unknown reference returns `404` with a stable error detail.

### `POST /api/trips`

Accepts `NewTrip`, validates the source, non-negative finite totals, non-empty item IDs and names, and non-negative finite item emissions. SQLite generates the ID and the server assigns the current UTC timestamp. The endpoint returns the canonical `SavedTrip` with status `201`.

### `DELETE /api/trips/{id}`

Resolves the path value by canonical backend ID or unique browser import key, deletes the resolved trip and its items, and returns `204`. This permits deletion from a legacy trip-detail URL after migration. An unknown reference returns `404`. SQLite foreign-key enforcement is enabled on every connection so item deletion cascades reliably.

### `POST /api/trips/import`

Accepts a migration batch:

```ts
interface ImportedTrip extends SavedTrip {
  // id is the original localStorage ID and acts as the import key.
}

interface ImportTripsRequest {
  trips: ImportedTrip[];
}
```

The endpoint validates every trip, imports the batch in one transaction, preserves each `savedAt`, assigns backend IDs, and returns the canonical backend `SavedTrip[]` in the same order. The original browser ID is stored as a nullable unique `importKey` on the backend trip row.

If an import key already exists, the endpoint returns that existing canonical record rather than inserting a duplicate. Repeating a full or partial client request therefore produces the same backend records. A conflicting reuse of an import key with different trip data returns `409` rather than silently changing history.

Malformed bodies and domain validation failures return `422`. Unexpected persistence failures return a controlled server error without partially committing a batch.

## 5. SQLite Model

`trips` stores:

- Integer primary key.
- Nullable unique browser import key.
- Source (`receipt` or `manual`).
- UTC saved timestamp.
- Total kg CO2e.

`trip_items` stores:

- Integer primary key.
- Trip foreign key with `ON DELETE CASCADE`.
- Stable frontend item ID.
- Item name.
- Item kg CO2e.
- Explicit item position so detail order is deterministic.

Indexes cover the unique import key, descending trip chronology, and the trip-item foreign key. Each connection enables foreign keys. Store methods use parameterized SQL and transaction boundaries. Timestamp ordering uses the trip ID as a deterministic secondary key.

Store lookup and deletion methods accept a durable reference rather than assuming every input is a canonical ID. They resolve canonical ID first and import key second, returning the same canonical domain record either way. The alias remains in SQLite for the lifetime of the trip, so resolution survives browser cleanup, reloads, and backend restarts.

The database defaults to `data/history.db` and remains configurable through `HISTORY_DB_PATH`. Database files stay excluded from Git while `data/.gitkeep` preserves the directory.

## 6. Backend Boundaries

`HistoryStore` owns SQLite initialization, CRUD/import operations, and canonical-or-legacy reference resolution. It accepts and returns normalized Python domain dictionaries; it does not know about FastAPI requests.

Pydantic request and response models in the API layer validate transport data and expose the camel-case JSON contract. Endpoint handlers translate between those models and the store.

`/api/receipts/scan` and `/api/receipts/analyze` remain calculation-only. This separation prevents manual calculations from appearing before explicit save and prevents duplicate receipt saves when the frontend repository performs its automatic save.

The existing `/api/history` and `/api/history/stats` endpoints from the implementation branch are not introduced. Progress stays derived from the repository data already required by History.

## 7. Frontend Repository Selection

`HttpTripRepository` implements the existing interface:

```ts
interface TripRepository {
  listTrips(): Promise<SavedTrip[]>;
  getTrip(id: string): Promise<SavedTrip | null>;
  saveTrip(trip: NewTrip): Promise<SavedTrip>;
  deleteTrip(id: string): Promise<void>;
}
```

It calls the Trips endpoints, validates returned JSON before exposing it to pages, maps `404` from `getTrip` to `null`, and converts network or invalid-response failures to `TripRepositoryError`.

`getTrip(id)` and `deleteTrip(id)` pass the route's identifier through unchanged. The backend resolves a migrated local ID and returns or deletes the canonical record, so the page does not need a transient client-side ID map.

Repository selection follows the existing API mode:

- `VITE_API_MODE=live`: use the migration-aware HTTP repository.
- Missing or `VITE_API_MODE=mock`: use `LocalStorageTripRepository`.

The repository base URL uses `VITE_API_BASE_URL`, with the existing local backend default. No page imports the HTTP or local-storage implementation directly.

## 8. Browser-to-SQLite Migration

Live-mode repository initialization performs this sequence before its first history operation:

1. Read and validate the current versioned local trip envelope.
2. If it is empty, continue directly to the requested HTTP operation.
3. Send the complete local collection to `POST /api/trips/import`.
4. Validate the complete canonical response.
5. Remove the migrated local records only after the server confirms the full batch.
6. Continue the original operation against the HTTP repository.

Initialization is guarded by one shared promise so concurrent startup reads or saves cannot launch duplicate migrations. The server's unique import key makes retry safe if the backend committed but the browser failed before local cleanup.

After migration, an existing `/history/{localStorageId}` route remains valid. Its repository lookup sends the original route value to `GET /api/trips/{id}`; the backend resolves the import key and returns the canonical trip. Deletion from that page sends the same legacy value and resolves the same row. Newly rendered History links use canonical IDs returned by the backend.

If migration fails, the local envelope is not changed. The current repository operation reports a controlled history error, and the next reload or operation after a new initialization retries migration. New live-mode saves do not bypass a failed migration, preventing old and new histories from being silently split.

Clearing migrated local records uses an explicit storage operation scoped only to `greenercart.saved-trips`; welcome preferences and unrelated site data remain untouched.

## 9. User Flows

### Receipt

1. The frontend calls the receipt scan endpoint.
2. The endpoint returns a calculation without persisting it.
3. Home maps the result to `NewTrip` and calls `saveTrip` automatically.
4. The HTTP repository returns the backend's canonical trip.
5. Calculation results remain visible if the history save fails.

### Manual

1. The frontend calls the manual analyze endpoint.
2. The endpoint returns a calculation without persisting it.
3. Home displays the result without a history write.
4. **Save to history** calls `saveTrip` once and adopts the canonical response.

### History, Details, Delete, and Progress

These pages continue to use only `TripRepository`. History receives newest-first trips, details loads by ID, delete removes through the repository, and Progress calculates insights across the six most recent uploads. No page changes its domain assumptions.

## 10. Error Handling and Data Integrity

- Pydantic rejects malformed request bodies before store calls.
- The store rolls back failed writes and imports.
- Imported timestamps must be valid timezone-aware ISO timestamps and are normalized to UTC.
- API errors use stable status codes: `404` missing, `409` import conflict, `422` invalid input, and `500` unexpected persistence failure.
- The HTTP repository rejects malformed success responses rather than introducing invalid trip data into the UI.
- Migration never deletes local data before a fully validated success response.
- Deleting a trip removes its items in the same transaction.

## 11. Testing and Verification

Backend store tests use a temporary SQLite database and cover:

- Schema initialization and enabled foreign keys.
- Canonical ID/timestamp assignment.
- Complete item round trips and deterministic ordering.
- Newest-first listing and single-trip lookup.
- Canonical and legacy-import-key lookup of the same trip.
- Deletion by canonical or legacy reference, item cascade, and missing-trip behavior.
- Atomic batch migration, timestamp preservation, idempotent retry, and import conflicts.

FastAPI tests override the production store and cover all endpoint status codes and JSON contracts. They verify that legacy lookup returns a canonical record, legacy deletion removes that record, and the alias remains resolvable after a new store instance opens the same database. They also prove that receipt and manual calculation endpoints do not write history.

Frontend tests cover:

- HTTP repository request methods, paths, payloads, canonical responses, `404`, network failures, and invalid JSON shapes.
- Mode-based repository selection.
- Successful one-time migration, timestamp preservation in the request, local cleanup after success, retry safety, and retained local data after failure.
- Loading and deleting through a pre-migration `/history/{localStorageId}` route after local cleanup.
- Existing automatic receipt save, explicit manual save, History, Trip Details, deletion, and six-upload Progress behavior.

Final verification runs the full Python test suite, frontend test suite, TypeScript/Vite production build, and an end-to-end live-mode smoke test against a temporary SQLite database.

## 12. Deferred Work

- Accounts, authentication, authorization, and per-user data isolation.
- Cloud database deployment and multi-instance coordination.
- Schema migration tooling beyond initial table creation.
- Pagination beyond the current complete hackathon history collection.
- Server-generated progress analytics or the implementation branch's all-time statistics endpoint.
- Offline live-mode writes after a migration or backend failure.
- Migrating unrelated browser preferences.

## 13. Success Criteria

- Live mode persists all new saved trips in SQLite through the canonical Trips API.
- Receipt calculations save automatically exactly once; manual calculations save only on request.
- History, Trip Details, delete, and six-upload Progress work without page-level persistence changes.
- Existing valid local trips migrate once, preserve their timestamps, receive backend IDs, and are removed locally only after success.
- Pre-migration trip-detail URLs and bookmarks continue to load and delete the migrated canonical trip through their durable legacy IDs.
- Repeated migration requests cannot create duplicates or silently overwrite conflicts.
- Mock mode remains fully functional with browser storage and without a backend.
- All backend and frontend tests pass, the production frontend builds, and the live end-to-end flow succeeds.
